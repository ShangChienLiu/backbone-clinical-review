# Further optimization options

Research reviewed November 25, 2026. The practical order for Backbone is to batch existing week reads, measure the remaining cost, and keep recomputation of a patient week in one shared evaluator. Each option below optimizes a different bottleneck.

## SQLite access paths and storage

SQLite can satisfy patient-first ordering with the existing `(patient_id, monday)` index. For a cohort filtered only by Monday, an index beginning with `monday` can narrow the scan and still require a separate patient-first sort. Check the actual plans on representative data because the planner can also choose a skip-scan after collecting statistics. [SQLite query planner](https://sqlite.org/queryplanner.html), [SQLite skip-scan](https://sqlite.org/optoverview.html#the_skip_scan_optimization), [SQLite query plan inspection](https://sqlite.org/eqp.html)

A local probe compared forced index plans on the same 250-patient, 6,000-week synthetic collection. It selected patient, Monday, and the verdict extracted from JSON, ordered by patient and Monday. For 750 matching weeks the median was 2.16 ms on the existing index and 1.95 ms on a temporary Monday-first index. For all 6,000 weeks the medians were 15.73 ms and 15.74 ms. These are warm SQL and row-fetch timings across nine runs. They exclude the cohort evaluator and index maintenance. Add the index only if narrow date ranges dominate and the end-to-end benefit persists when corrections are included.

If decoding JSON remains expensive, benchmark a small typed projection for date bounds, solver version, result status, and coverage flags. In SQLite, a `STORED` generated column computes its value on write and uses disk space. Adding one to an existing table requires a rebuild. A transactionally maintained projection table is another migration option. SQLite JSONB avoids reparsing text, but most field lookups still take linear time in the payload size. Measure read latency, amendment latency, and database growth together before choosing a format. [SQLite generated columns](https://sqlite.org/gencol.html#virtual_versus_stored_columns), [SQLite JSONB](https://www.sqlite.org/json1.html#jsonb)

## Reuse only the work that pays off

Noria's research prototype materializes queried keys and reconstructs missing state on demand. Apply that idea inside SQLite if users repeatedly request the same clipped weeks. Store only frequently reused exact slices, keyed by patient, start and end dates, solver version, and the relevant evidence revision. Evictable slices must behave like a recomputation when absent. Keep batch reads, fallback evaluation, and any supporting evidence reads in one snapshot so a correction cannot mix old and new results in one response. [Noria at OSDI](https://www.usenix.org/conference/osdi18/presentation/gjengset), [SQLite read transactions](https://sqlite.org/lang_transaction.html#read_transactions_versus_write_transactions)

For updates, one patient can have many weeks and a single correction can affect both the old and new date ranges. Track affected keys, then choose the cheaper of reevaluating the affected slices or rebuilding the patient's projection. OpenIVM compiles SQL to incremental refresh SQL and documents partition-level recomputation for window functions and an experimental cost model. Its DuckDB extension is currently under testing. The useful near-term idea is the choice between incremental work and a rebuild. Measure the crossover on batches with different numbers of affected patients and weeks, and compare each result with the same uncached evaluator. [OpenIVM paper](https://ir.cwi.nl/pub/34276/), [OpenIVM implementation](https://github.com/openivm/openivm), [Cost model](https://github.com/openivm/openivm/blob/main/docs/internals/cost_model.md)

## Continuous results and offline analytics

For several continuously refreshed cohort views, consider emitting one removed and one added patient-week result when a correction changes it. DBSP formalizes incremental maintenance over insertions and deletions. Materialize uses indexed change collections and can share arrangements across queries. Applied here, the clinical evaluator still determines coverage and conflicts. A downstream engine consumes the resulting changes at a committed revision. A single changed week can affect each neighboring pair. Retain original evidence and use the commit revision to order changes, because some signed corrections amend old service dates. Feldera's `LATENESS` settings can discard updates when the old version falls outside the configured window. Use that policy only for derived views with a separately replayable ledger. [DBSP journal paper](https://doi.org/10.1007/s00778-025-00922-y), [Materialize arrangements](https://materialize.com/docs/fundamentals/concepts/arrangements/), [Feldera lateness](https://docs.feldera.com/tutorials/time-series/)

For wide offline audits, export one pinned revision of typed week rows with stable evidence IDs. DuckDB reads selected Parquet columns and pushes filters into the scan. Its 2.0 Parquet reader can also use page indexes when present. Consider an export once repeated long-range scans compete with interactive reviews. Compare export time plus scan time, and keep source evidence accessible at the same revision. [DuckDB Parquet documentation](https://duckdb.org/docs/2.0/data/parquet/overview)

Adopt changes that preserve the patient-week verdicts, date bounds, and evidence identifiers. Include missing and stale cache rows, unclear coverage, late corrections, and concurrent imports in the comparison. Record p95 latency and write amplification alongside the result diff.
